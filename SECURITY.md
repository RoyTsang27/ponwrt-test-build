# Security

Release builds must run from the default branch and use the protected `release`
GitHub environment. Configure required reviewers and restrict that environment
to the default branch in repository settings. Allow GitHub Actions to create
pull requests if you want the kernel update workflow to propose updates.

Set these environment secrets before running the release workflow:

| Secret | Contents |
| --- | --- |
| `PONWRT_APK_PRIVATE_KEY` | Stable PEM package signing private key, generated with `openssl ecparam -name prime256v1 -genkey -noout` |
| `PONWRT_USIGN_PRIVATE_KEY` | Stable firmware private key generated by `usign -G` |
| `PONWRT_USIGN_PUBLIC_KEY` | Corresponding firmware public key generated by `usign -G` |

Generate keys on a trusted system, retain an offline backup, and transfer them
directly into GitHub secrets. Never commit private keys or paste them into logs.
The APK key and firmware key serve different formats and are not interchangeable.
Release builds fail when keys are missing or the firmware key pair does not match.

Released images require a trusted firmware signature during sysupgrade. The
firmware public key is installed in `/etc/opkg/keys`, which is the verifier's
trust directory even when packages use APK. Keep the same firmware key between
releases. For a planned rotation, deploy the next public key to existing devices
through a release signed with the current key first. `sysupgrade -F` remains an
explicit recovery override; do not use it for routine upgrades.

Local builds generate local firmware keys, and signature enforcement is opt-in
through `CONFIG_REQUIRE_IMAGE_SIGNATURE`. A local key is not trusted by a device
running a release signed with another key.

Package builds execute source code, including feed build scripts. The release
signing job therefore trusts the checked-out repository, pinned feeds, build
tools, and runner. Pinning and late key loading reduce exposure; they do not
isolate a signing key from a compromised build. Review feed lock updates and
protect the release environment. SHA256 archive checksums detect corruption but
are not a substitute for authenticated firmware signatures.

Use `feeds.conf.release` for release builds. Update its commits deliberately and
verify both AN7581 and AN7583. Development builds using `feeds.conf.default`
continue to follow upstream feed branches.

The kernel tracking workflow runs weekly and can be dispatched manually. It
proposes newer OpenWrt Airoha patch levels as draft PRs and runs the kernel
compilation workflow on the proposed branch. It refuses downgrades, checksum
changes without a version change, and a move to another kernel series. A series
change requires rebasing the Airoha patch stack, including PON and offload
support. Before merging any bump, build both targets and test them on hardware.
Builds currently use upstream BBR. The preserved BBRv3 patch in
`target/linux/generic/experimental-6.18/` is inactive because it conflicts with
Linux 6.18.55 TCP/MPTCP internals. It needs a separate rebase and validation.

GitHub token permission settings or exhausted Actions quotas can prevent these
checks; review failed scheduled runs.

The shipped configurations select LuCI HTTPS support. New installations should
enable HTTPS and redirect HTTP when the TLS backend is present. Existing saved UCI
configuration can preserve HTTP settings; check `uhttpd` after upgrading. Set a
unique root password immediately on first boot, on an isolated trusted LAN.
Factory calibration and PON identity backups contain sensitive device data.

See [the audit report](docs/SECURITY-AUDIT.md) for findings and validation limits.
For vulnerability reports, use GitHub's private vulnerability reporting feature
when enabled, or arrange a private channel with the repository owner. Avoid
publishing credentials, calibration data, or exploit details in a public issue.
